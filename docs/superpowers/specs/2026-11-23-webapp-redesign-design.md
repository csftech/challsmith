# web app 介面改版設計文件

日期：2026-11-23

## 1. 目的

challsmith 的出題 web app 目前是簡單的表格與 inline style，看起來不夠現代，題目也只能照建立順序列出。這次改版要達成四件事：

1. 換上現代、不像 AI 範本的介面，而且可以切換四種主題。
2. 題目頁可以在列表與卡片之間切換。
3. 題目的排列和新人在 CTFd 看到的完全一樣，作者可以直接拖拉調整，並同步回 CTFd。CTFd 後台只能一題一題改 `position` 數字，很難調整順序，這是改版的主要動機。
4. 介面可以切換繁體中文與英文。

使用者是出題與管理的人（`aps` 帳號，從 VM 上的瀏覽器開 `http://127.0.0.1:3000`），不是新人。新人只會看到 CTFd，CTFd 本身的佈景不在這次範圍內。

## 2. 目標、非目標與反目標

### 目標

- 所有頁面（登入、題目、新增題目、編輯器、發佈、Git 同步、發佈前清理）都換成新的版面，共用左側導覽列。
- 四種主題可以切換，預設 G，選擇記在 cookie。
- 題目頁依分類分組，題目可以在分類內拖拉，分類可以整組拖拉。存檔後 CTFd 的分類順序與題目順序和 web app 一致。
- 題目頁可以切換列表與資訊卡兩種顯示方式，選擇記在瀏覽器。
- 繁中與英文切換，預設繁中，選擇記在 cookie，伺服器端產生頁面時就用正確的語言。後端錯誤也依語言顯示。

### 非目標

- 不更動 CTFd 題目 id。使用者評估過重新編號的做法後決定放棄（見第 9 節）。
- 不修改 CTFd 的佈景與新人看到的畫面，只改題目的 `position`。
- 不翻譯發佈記錄裡 docker build 與工具本身的輸出，也不翻譯 CLI（`cleanup.sh`）的輸出。
- 不做參考圖裡與出題無關的功能，例如封存、釘選、多選批次操作。

### 反目標

- 介面帶有明顯的 AI 範本感：紫色漸層、大量 emoji、毛玻璃、每個區塊都是大圓角卡片加陰影。
- 拖拉之後 web app 顯示的順序和新人在 CTFd 看到的不一樣。
- 切換語言或主題時，畫面先閃一下舊的語言或主題。
- 在中文介面下夾雜沒有翻譯的英文介面字串（後端未知錯誤的原文除外，見 6.3）。

## 3. 現況

- 前端：Next.js 16、React 19.3、TypeScript 7，BFF 架構（`frontend/app/api/[...path]` 轉送到後端），頁面多為 client component，樣式是 `globals.css` 加上大量 inline style，中文字串直接寫在 11 個檔案裡。測試是 `node --test lib/`。
- 後端：FastAPI，`challenges` 表沒有排序欄位，`GET /challenges` 依建立順序回傳。錯誤由 `services/errors.py` 的 `DomainError` 子類別拋出，`main.py` 轉成 `{"detail": "..."}`，訊息都是英文。
- CTFd 3.8.9 的題目有 `position` 欄位（整數，預設 0），管理 API 可以修改。題目清單 API（`get_all_challenges`）的排序是：`position` 大於 0 的題目依 `position` 由小到大排在前面，`position` 為 0 的題目排在最後並依分數排序。CTFd 前台依分類分組，分類的先後取決於該分類的題目在上述順序中第一次出現的位置。目前所有題目的 `position` 都是 0。

## 4. 做法的選擇

### 4.1 排序的呈現方式

| 做法 | 說明 | 結果 |
|---|---|---|
| A. 依分類分組（採用） | 題目在分類內拖拉，分類整組拖拉，存檔時依畫面順序把 `position` 設成 1、2、3…… | web app 的畫面就是新人看到的畫面 |
| B. 不分組的單一清單 | 拖拉一條清單，順序直接對應 `position` | 不同分類交錯時，CTFd 仍會分組，兩邊順序不一致，不採用 |

### 4.2 語言切換

| 做法 | 說明 | 結果 |
|---|---|---|
| A. 自己寫對照表 | 不加套件，型別檢查兩種語言的 key | 未採用 |
| B. next-intl（採用） | Next.js 常用的翻譯套件，不使用網址前綴，語言記在 cookie | 使用者選擇 |

兩種做法的後端錯誤都需要加上固定的錯誤代碼，前端才能翻譯。

### 4.3 主題

使用者看過 D、E、F、G 四種風格的 mockup 後，決定四種都要，用切換按鈕切換，預設 G。卡片模式採用「資訊卡」版面（第 1 種）。

mockup 隨本文件存放在 `docs/superpowers/specs/assets/2026-11-23-webapp-redesign/`：`visual-style-v2.html` 是四種主題，`card-view.html` 是卡片版面。兩者是顏色、框線、圓角、字體與版面配置的正本，用瀏覽器直接打開即可，實作時照著它們的 CSS 數值做。mockup 裡的「CTFd id」欄位與範例資料只是示意。

## 5. 介面設計

### 5.1 主題

四種主題都用同一套版面，差異只在 CSS 變數，以 `<html data-theme="...">` 切換：

| id | 名稱（中／英） | 特色 |
|---|---|---|
| `signal`（G，預設） | 工程／Signal | 米白底、黑色 1.5px 框線、直角（圓角 2px）、IBM Plex Sans 與 IBM Plex Mono、表頭與分類標題用等寬大寫字、唯一的重點色是訊號黃 `#f5d90a` |
| `zinc`（D） | 灰階／Zinc | 鋅灰色系、白底、1px 細框線、圓角 7 到 10px、Inter、主按鈕黑色 |
| `midnight`（E） | 深色／Midnight | 近黑底 `#0e0f11`、低對比邊框、Inter、主按鈕藍色 `#4c8dff` |
| `canvas`（F） | 浮動／Canvas | 淡藍灰畫布 `#eef1f5`，側欄與內容是兩塊有留白的白色圓角面板，主色 `#2f5bd3`，分類標籤依分類上色 |

變數至少涵蓋：背景（畫布、側欄、內容、面板）、文字（主要、次要）、框線顏色與粗細、圓角、主按鈕色、狀態標籤色、字體（內文、等寬）、面板外距（`canvas` 有留白，其他為 0）、表頭樣式（`signal` 為等寬大寫）。中文一律用 Noto Sans TC。

字體以 `@fontsource` 套件自行提供，不在執行時連 Google Fonts。VM 的 build 走公司的 npm mirror，執行時也不應依賴外部網路。

編輯器（CodeMirror）在 `midnight` 主題使用深色配色，其他主題用淺色配色。

### 5.2 版面

- **左側導覽列**：品牌、分組的導覽項目（出題：題目、新增題目；系統：Git 同步、發佈前清理），底部顯示登入帳號與登出。窄螢幕時可以收合。
- **頂列**：收合側欄的按鈕、目前頁面名稱、題目搜尋（快捷鍵 `/`，僅題目頁）、語言切換、主題切換。
- 登入頁沒有側欄，置中顯示，同樣有語言與主題切換。

### 5.3 題目頁

工具列：分類篩選、狀態篩選、題數統計（例如「4 題 · 2 已發佈」）、列表／卡片切換、新增題目按鈕。

狀態沿用現有的三種發佈狀態（草稿、已發佈、有未發佈的修改），以及 git 同步狀態。

**列表模式**：依分類分組，每組有分類標題（拖拉把手、收合箭頭、名稱、題數）。欄位：拖拉把手、CTFd id（未發佈顯示「—」）、名稱與 slug、分類、分數、發佈狀態、git 同步狀態、更新時間、操作（編輯、發佈、刪除）。

**資訊卡模式**：依分類分組，每組一列卡片，寬螢幕一列三張。卡片內容：拖拉把手、名稱、發佈狀態、slug 與 CTFd id、範本名稱、服務數、分數、更新時間、操作按鈕。點卡片名稱進入編輯器。

**操作**：編輯開啟編輯器，發佈前往發佈頁，刪除需要在確認對話框輸入 slug（沿用現有刪除 API）。

**拖拉**：

- 題目只能在同一個分類內移動。要換分類，請到編輯器修改分類。
- 分類標題可以整組上下移動。
- 有搜尋或篩選條件時停用拖拉，並顯示提示，因為部分題目被隱藏時，無法決定拖拉後的完整順序。（設計者的決定）
- 鍵盤也能操作拖拉：聚焦把手後按空白鍵拿起，方向鍵移動，再按空白鍵放下。
- 放下後立即呼叫儲存順序的 API（見 6.2），儲存中顯示進度，失敗時顯示錯誤並重新載入 CTFd 目前的順序。

### 5.4 其他頁面

新增題目、編輯器、發佈、Git 同步、發佈前清理的功能與流程不變，只換成新的版面、元件與主題，字串改用翻譯。

## 6. 後端設計

### 6.1 排序資料

- `challenges` 表新增 `position INTEGER NOT NULL`，以 Alembic migration `0002` 加入。現有資料依 `created_at` 依序給 1、2、3……，第一次載入題目頁時再依 CTFd 的順序校正（見下方）。
- 新建立、匯入（git 匯入或壓縮檔匯入）的題目，`position` 為目前最大值加 1，也就是排在最後。
- `position` 只存在資料庫，不寫進 `challenge.yml`，也不影響 `sync_hash`。否則每次調整順序，所有題目都會變成「有未匯出的修改」。（設計者的決定）

### 6.2 API

**`GET /challenges`**：回傳順序改為：

1. 向 CTFd 讀取所有題目的 `position`（管理員檢視，含隱藏題目）。
2. 「已發佈」指 `ctfd_id` 在 CTFd 裡確實存在的題目。`ctfd_id` 指向 CTFd 已經不存在的題目（例如在後台被刪掉）時，視為未發佈：回應帶上 `ctfd_missing: true`，畫面標示「CTFd 上找不到」，儲存順序時跳過它，下次發佈會重新建立。（設計者的決定）
3. 已發佈題目之間的相對順序以 CTFd 為準，採用 CTFd 清單 API 的排序規則（`position` 大於 0 的由小到大，`position` 為 0 的放最後並依分數排序，同分再依 id）。已發佈題目依這個順序，依序填回資料庫順序中原本由已發佈題目佔據的位置，未發佈題目的位置不動。（設計者的決定）
4. 最後依分類重新分組：分類的先後取決於該分類在上一步結果中第一次出現的位置，分類內保持上一步的相對順序。這和 CTFd 前台的分組方式一致，也保證結果符合儲存順序時「同分類連續」的規則，即使有人在 CTFd 後台把同分類的題目排得不連續也一樣。
5. 若校正後的順序和資料庫不同，只寫回資料庫，不寫回 CTFd。CTFd 的 `position` 要到第一次拖拉存檔才會寫入，在那之前兩邊靠相同的排序規則保持一致。以目前所有 `position` 都是 0 的狀況，第一次載入時順序會變成依分數排序，這正是新人目前在 CTFd 看到的順序。
6. CTFd 連不上時，直接用資料庫的順序，回應帶上一個旗標，前端顯示「無法讀取 CTFd 的順序」的提示，並停用拖拉。

隱藏題目（`visible: false`）不會出現在 CTFd 前台。因為儲存時同分類必定連續，CTFd 前台的分類順序等於各分類區塊在 web app 中的先後，隱藏題目不會讓兩邊分歧。整個分類都隱藏時，該分類只是不出現在前台。

每筆題目多回傳 `position`、`ctfd_id`、範本名稱、服務數、分數與 `updated_at`，供列表與卡片顯示。分類順序不需要另外儲存，由題目順序推導。

**`PUT /challenges/order`**：請求本體是所有題目 slug 依新順序排列的陣列。

1. 驗證陣列剛好包含所有題目，不多不少、沒有重複，否則回 400（`order_mismatch`）。
2. 驗證同一分類的題目在陣列中是連續的，否則回 400（`order_category_split`）。
3. 依陣列順序把 `position` 設為 1 到 N。
4. 對每一題已發佈的題目（不含 `ctfd_missing` 的題目），呼叫 CTFd `PATCH /api/v1/challenges/{id}`，只送 `position`。
5. CTFd 全部成功才提交資料庫。任一題失敗就回滾資料庫並回 502（`ctfd_order_failed`），訊息列出失敗的題目。此時 CTFd 可能已經更新了一部分，前端會重新載入，以 CTFd 的實際順序為準。
6. 發佈正在執行時也可以調整順序，發佈不會受影響（見下一點）。

**發佈**：`ctfd_payload` 加上 `position`。值在呼叫 CTFd 建立或更新題目的當下從資料庫讀取，不使用發佈開始時的值，避免發佈期間調整的順序被舊值蓋掉。

**在編輯器修改分類**：儲存題目資訊時若分類改變，把這題移到新分類的最後一題之後；新分類原本不存在時，移到整份清單的最後。接著把所有題目的資料庫 `position` 重新編成 1 到 N，只動資料庫。分類本身要到重新發佈才會更新到 CTFd，所以發佈成功後，再把所有已發佈題目的 `position` 同步到 CTFd（同 `PUT /challenges/order` 第 4 步，失敗只記錄警告，不讓發佈失敗）。（設計者的決定）

**路由**：`PUT /challenges/order` 要在 `PUT /challenges/{slug}` 之前註冊，並把 `order` 加入保留字，不允許用作 slug。

**順序規則的實作位置**：校正（GET）、驗證與重新編號（PUT、修改分類）都放在同一個 service 的純函式裡，以題目清單和 CTFd 的 `position` 為輸入，方便單元測試。

`ctfd_client` 新增讀取所有題目 `position` 的方法（管理員檢視，含隱藏題目）與只更新 `position` 的方法。只有 client 層呼叫 CTFd，排序規則放在 service 層，依現有的分層規則。

### 6.3 錯誤代碼

- `DomainError` 新增 `code` 屬性，回應改為 `{"detail": "...", "code": "..."}`。`detail` 維持英文原文，給記錄與除錯用。
- 每個會顯示給使用者的錯誤都要有固定的 `code`，例如 `unauthorized`、`not_found`、`slug_exists`、`publish_running`、`cleanup_running`、`order_mismatch`、`order_category_split`、`ctfd_order_failed`、`ctfd_unreachable`。實作時盤點所有 `DomainError` 的拋出點逐一命名。
- 前端在 `errors.<code>` 底下提供兩種語言的訊息，可以帶參數，例如失敗的題目名稱。沒有 `code` 或沒有對應翻譯時，顯示 `detail` 原文。

## 7. 語言切換

- 使用 next-intl 4.15.3，採用不帶網址前綴的模式：語言存在 cookie `NEXT_LOCALE`，值為 `zh-TW` 或 `en`，預設 `zh-TW`。
- 翻譯檔放在 `frontend/messages/zh-TW.json` 與 `frontend/messages/en.json`，依頁面分區。啟用 next-intl 的型別擴充，讓用到不存在的 key 時型別檢查失敗，另外再寫一個測試確認兩個檔案的 key 完全一致。
- 切換語言時寫入 cookie 並重新整理頁面，伺服器端產生頁面時就是新的語言。
- `<html lang>` 跟著語言設定。日期與相對時間（例如「2 小時前」）用 next-intl 的格式化，依語言顯示。

## 9. 已經放棄的做法：重新編號 CTFd 題目 id

使用者希望 CTFd 題目 id 從 1 開始並依順序遞增。評估結果如下，使用者決定放棄：

- CTFd 有 11 張資料表以外鍵引用題目 id，更新規則都是禁止修改（`RESTRICT`）。chall-manager 以題目 id 記錄 instance，題目的前置條件以 JSON 存 id，web app 也記錄 `ctfd_id`。
- 可行的做法是刪除所有題目、把 `AUTO_INCREMENT` 重設為 1、再依順序重新發佈，但這會清掉作答紀錄，也會清掉直接在 CTFd 後台建立的內容，而且之後拖拉只改 `position`，id 很快又會和順序不一致。

## 10. 測試

- **後端單元測試**：
  - `ctfd_id` 在 CTFd 不存在的題目視為未發佈，儲存順序時跳過；修改分類後移到新分類最後並重新編號；CTFd 的順序把同分類拆散時，結果仍依分類連續。
  - `GET /challenges` 的順序校正：CTFd 順序與資料庫不同時，以 CTFd 為準；未發佈題目保留位置；`position` 為 0 的題目依分數排序；CTFd 連不上時退回資料庫順序並帶旗標。
  - `PUT /challenges/order`：成功時資料庫與 CTFd 都更新；陣列缺題、多題、重複時回 400；同分類不連續時回 400；CTFd 任一題失敗時回滾並回 502。
  - 發佈時帶上當下的 `position`。
  - 新建立與匯入的題目排在最後。
  - 錯誤回應帶有 `code`。
- **前端測試**（`node --test`）：兩個翻譯檔的 key 一致；分組與排序的純函式（由題目清單推導分類順序、拖拉後產生新的 slug 陣列）。
- **型別檢查**：`tsc --noEmit` 涵蓋翻譯 key。
- **端對端測試**（dev VM）：用 API 調整順序後，CTFd 管理 API 回傳的 `position` 和 web app 一致，CTFd 前台清單 API 的分類順序也一致；現有的發佈、清理等端對端測試照樣通過。
- **手動驗證**：四種主題與兩種語言的所有頁面截圖檢查；用滑鼠和鍵盤各拖拉一次。
